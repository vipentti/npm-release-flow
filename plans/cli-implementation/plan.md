# CLI (prepare/tag/check) and workflow job bodies for npm-release-flow

## Summary

Implement the npm-release-flow CLI command set (`prepare`/`tag`/`check`, dry-run default, `--execute` mutation, exit codes 0/1/2, error-content contract, recoverability, one cross-platform spawn helper) per blueprint §8, and replace the placeholder workflow job bodies (detect/verify/release, blueprint §5) with real bodies invoking kit scripts at `.npm-release-flow/src/...` per §5-§10. The bin stub already declares the surface: `npm-release-flow <prepare|tag|check> [--execute]`.

Blueprint pin: every §N reference in this plan and in tasks.md resolves to `vipentti/agent-blueprints` at commit `f9d06c77b9920e4cfab774d254f22d60894c1f05`, file `blueprints/npm-release-flow.md`. No other blueprint revision is authoritative for this work. Behavior reference: Planlet's working flow (`vipentti/planlet` `scripts/release.mjs`, `scripts/detect-release-merge.mjs`, `.github/workflows/release.yml`), generalized and package-shaped.

## Scope

- `bin/npm-release-flow.mjs` (replaces the placeholder): argument parsing via `node:util` `parseArgs`, dispatch to the three commands, exit-code plumbing. Usage on stderr + exit 1 for missing/unknown subcommand or unknown flag. `prepare` and `tag` take a required `--version X.Y.Z` (caller supplies the version, per the concept doc); `check` takes no flags; `--execute` is accepted by all three and is a no-op on `check` (nothing to mutate).
- `src/` layout: `src/lib/` shared modules (spawn, errors, versions, changelog, control-files, release-state, tag-verify, pack-contract, skew, repo-state, app-token), `src/commands/{prepare,tag,check}.mjs`, `src/detect.mjs`/`src/verify.mjs`/`src/release.mjs` job scripts plus `src/revalidate.mjs` and `src/validate-artifact.mjs` job-side helpers, `src/index.mjs` re-exports the public surface (the bin's `main` plus the shared libs). Plain `.mjs`, no build step (§3); typechecked by the existing `tsconfig.json` scope.
- `src/lib/spawn.mjs`: the single subprocess helper (blueprint §8 "one spawn helper owns subprocess execution"): sync and async variants, captures stdout/stderr, resolves Windows `.cmd` wrappers there once (win32 spawns through the shell per PATHEXT, POSIX spawns argv directly), non-zero exit raises a typed error carrying stdout/stderr. No other module spawns a subprocess.
- `src/lib/errors.mjs`: the exit-code taxonomy (0 success, 1 error, 2 no-op/already done, §8) and the error-content contract (every failure message states what was checked, what state was actually found, and the correction action).
- `prepare` (concept doc flow): require clean worktree and HEAD at `origin/main`; require `--version` to be stable X.Y.Z and greater than the current version; require no conflicting local/remote `release/vX.Y.Z` branch, no open release PR, no conflicting tag; require non-empty `## [Unreleased]` changelog section; cut the changelog (`## [x.y.z] - date`, link-reference and compare-URL rewrite), bump `package.json` and `package-lock.json` version fields (root `version` and `packages[""]`), revalidate the resulting release state, create the branch, create the signed commit `release: X.Y.Z` (`git commit -S`; refuses when signing is unavailable, never unsigned), verify post-commit (message, one parent, `git verify-commit`, changed-file set exactly the three control files), push, `ls-remote` verify the remote ref equals the pushed SHA, create the PR via `gh pr create` stamping the machine-readable kit-version marker in the PR body (§10 skew marker), return to `main`. Dry-run default prints every would-mutation and stops before the first mutation; `--execute` performs them. Rerun semantics per §9 boundaries 1-2: refuse with distinct messages (local branch exists / remote branch exists / open PR exists / merged: "version already prepared" / closed-unmerged: manual action); `prepare` never resumes, operator resolves then reruns from the start. Exit 2 only for genuinely already-done states (open release PR exists, version already prepared/merged); exit 1 for partial-conflict and manual-action states (conflicting local or remote branch, closed-unmerged PR), which need correction, not a benign no-op.
- `tag` (break-glass local recovery, concept doc; deliberately separate from the automated path, which is: PR merge -> protected job -> tag + publish): the tag target is explicitly the release-merge commit on `origin/main` (the merged release PR's commit, the same commit the automated path tags; `prepare`'s signed branch commit is not the target). Before any tag creation the command resolves the target deterministically: clean worktree and `origin/main` fetched; walk `origin/main`'s first-parent history and find exactly one matching release merge for the requested version using the documented merge-message grammar (`Merge pull request #N from <owner>/release/v<version>`), zero or multiple candidates -> refusal; run the §9 release-state classification on the candidate commit against its first parent and require a valid release for the requested version (a release-like merge message whose diff is not a valid release -> refusal); validate `package.json`, `package-lock.json`, and changelog from the candidate commit, not the current worktree (version fields match the requested version, lockfile identity, valid released section `## [x.y.z] - date`). Wrong target -> refusal. On the resolved target it creates the annotated, signed tag `vX.Y.Z` with subject `Release vX.Y.Z` as create-then-verify-then-push (no partial-mutation window, §6), verifies it fully (annotated object, target, subject, `git verify-tag --raw` yielding exactly one `VALIDSIG` whose primary fingerprint equals the configured `NPM_RELEASE_FLOW_GPG_FINGERPRINT` env value), pushes with the App token (T11 holds on the local recovery path too: the tag push authenticates as the release GitHub App, never with the operator's credentials, which the `refs/tags/v*` creation ruleset would reject anyway since its only bypass actor is the release App), verifies the remote tag object equals the local one. The command obtains the App identity the same way the workflow does: `NPM_RELEASE_FLOW_APP_ID` read from the repository variable via `gh api`, plus `NPM_RELEASE_FLOW_APP_PRIVATE_KEY` from the local environment (secrets are never API-readable, so the operator must export it), both non-empty asserted, and mints the installation token via the shared `src/lib/app-token.mjs` helper (same JWT + API exchange the pinned `actions/create-github-app-token` performs); it refuses when the material is absent or the token cannot be minted. `--execute` performs create+push (a create-only mode has no use case: recovery always ends in a push; dry-run reports both); without `--execute` it prints the plan. Completion semantics per §9 boundary 4: remote valid tag -> fetch + full verify, exit 0 (no push); remote divergent tag -> exit 1, manual; remote absent with a valid local tag -> dry-run reports the push and `--execute` pushes that existing tag with the App token, then verifies the remote object; remote absent with no local tag -> create, verify, push, verify. Refuses to proceed unsigned or with a lightweight tag.
- `check` (non-mutating setup validation, §8): verifies the consumer's release prerequisites: the three control files (CHANGELOG.md with a `## [Unreleased]` section, `release:verify` script declared in package.json, committed lockfile), secrets and variables presence by name via `gh api` (names only, never values: `actions/secrets`, `actions/variables`), the `release` Environment exists AND carries required-reviewer protection (protection rules inspected via `gh api`; an Environment without required-reviewer protection is a failure: it provides no approval gate, T3/§10 step 5), local git/gh state (`gh auth status`, git identity, local GPG availability, `NPM_RELEASE_FLOW_GPG_FINGERPRINT` set to 40-hex), and App-tag path readiness (`NPM_RELEASE_FLOW_APP_ID` variable present via `gh api`; `NPM_RELEASE_FLOW_APP_PRIVATE_KEY` non-empty in the local environment; the App installation resolves for the repository via `gh api`, T11). Exit 0 when everything passes; exit 1 listing every problem with the error-content contract; never mutates.
- Workflow job bodies (`.github/workflows/release.yml`, the §5 interface and scaffolded permissions/outputs stay untouched): real bodies per job, invoking kit scripts at `.npm-release-flow/src/...`:
  - `detect` job: env `BEFORE_SHA: ${{ github.event.before }}` and `GH_TOKEN: ${{ github.token }}`; step runs `node .npm-release-flow/src/detect.mjs`; the step binds HEAD to `GITHUB_SHA` and writes the declared outputs (`is-release`, `version`) via `GITHUB_OUTPUT`. The script validates the §4 mandatory consumer prerequisites (CHANGELOG.md with a `## [Unreleased]` section, a `release:verify` script declared in package.json, a committed lockfile; any missing prerequisite -> hard fail, missing ⇒ detect fails, §4) before emitting any verdict, ordinary or release, then classifies per the §9 enumeration table (every row: ordinary push -> exit 0, `is-release=false`, no PR or skew-marker lookup; valid release merge -> exit 0, `is-release=true`, version; every ambiguous row -> hard fail exit 1), and performs the §10 skew-marker read only on the valid-release branch: resolve the merged PR number from the triggering commit's merge message, read the PR body via `gh api`, extract the kit-version marker, compare against `.npm-release-flow/package.json` version; unparseable merge message, missing/unreadable marker, or mismatch is a hard fail (T9, fail closed). Ordinary pushes never touch the PR API.
  - `verify` job: env `VERSION` and `GH_TOKEN`; a setup-node step (`actions/setup-node@820762786026740c76f36085b0efc47a31fe5020`, v7.0.0) selects the consumer's Node from `package.json.engines.node`, falling back to Node 22 when absent (§7), before `npm ci`; the step runs `node .npm-release-flow/src/verify.mjs`, which runs `npm ci`, `npm run release:verify`, a defensive re-validation of the §4 mandatory checks (enforcement lives in detect, §4), build-if-declared, bin-entry checks, `npm pack --json --ignore-scripts`, the pack contract (exactly one tarball, safe filename, name/version match the manifest and release version, integrity metadata matches the bytes), the generic smoke test (`npm i <tgz> --ignore-scripts --omit=peer` in a temp project, declared binaries resolve), the T9 skew check (consumer's installed kit version vs the checkout's version), and writes `package-sha256` via `GITHUB_OUTPUT`. Job body adds `actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a` (v7.0.1) (fixed name `npm-release-flow-${{ github.sha }}`, tarball + pack.json, `if-no-files-found: error`).
  - `release` job body (step order is the trust boundary, §6 load ordering + §9 revalidation): (1) consumer checkout at the triggering SHA (`actions/checkout` pinned, `ref: ${{ github.sha }}`, `fetch-depth: 0`, `persist-credentials: false`) before any probing or revalidation, (2) the existing guarded kit checkout into `.npm-release-flow` at `job.workflow_sha` (unchanged), (3) setup-node pinned at `820762786026740c76f36085b0efc47a31fe5020` (v7.0.0) for exact Node 24.11.1 (§7; npm 11.6.2 is that Node release's bundled npm, there is no `npm-version` input) with exact-version assertion of both `node --version == v24.11.1` and `npm --version == 11.6.2`, fail closed before any mutation, (4) tag probe (`git ls-remote` for `refs/tags/v<version>` -> `tag-exists` output, step id `tag-probe`), (5) revalidation #1 via `node .npm-release-flow/src/revalidate.mjs` (ancestry: triggering SHA reachable from `origin/main`; control-file equality: `git diff --quiet` over the three files; GH_TOKEN only, no secrets), (6) `actions/download-artifact@3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c` (v8.0.1), (7) `node .npm-release-flow/src/validate-artifact.mjs` with `PACKAGE_SHA256: ${{ needs.verify.outputs.package-sha256 }}` (downloaded tarball sha256 equals it; pack.json contract: name/version/integrity; bin entries resolve; writes `PACKAGE_TARBALL` to `$GITHUB_ENV`), (8) fresh `GNUPGHOME` init (`mktemp -d`, chmod 700, exported via `$GITHUB_ENV`), (9) public-key config step (only when `tag-exists=true`, verify-only path: step-scoped non-empty assertion of `NPM_RELEASE_FLOW_GPG_PUBLIC_KEY`, then import, fingerprint 40-hex, exactly one primary public key, no secret keys in the home), (10) private-key config step (only when `tag-exists=false`: step-scoped non-empty assertions of `NPM_RELEASE_FLOW_GPG_PRIVATE_KEY` and `NPM_RELEASE_FLOW_GPG_PASSPHRASE`, passphrase file chmod 600, import private key, exactly one primary secret key, fingerprint match, gpg-wrapper + git identity from `NPM_RELEASE_FLOW_GIT_NAME`/`GIT_EMAIL` vars), (11) revalidation #2 (same `src/revalidate.mjs`, immediately before tag creation, TOCTOU guard), (12) step-scoped non-empty assertion of `NPM_RELEASE_FLOW_APP_PRIVATE_KEY` immediately before `actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1` (v3.2.0; only when `tag-exists=false`; `NPM_RELEASE_FLOW_APP_ID` var, T11), (13) `node .npm-release-flow/src/release.mjs` (mutation orchestration below) with named env `VERSION: ${{ needs.detect.outputs.version }}`, `TAG_EXISTS: ${{ steps.tag-probe.outputs.tag-exists }}`, `NPM_RELEASE_FLOW_GPG_FINGERPRINT: ${{ vars.NPM_RELEASE_FLOW_GPG_FINGERPRINT }}`, `NPM_RELEASE_FLOW_APP_TOKEN: ${{ steps.release-app-token.outputs.token }}` (only when `tag-exists=false`), `GH_TOKEN: ${{ github.token }}` (`GNUPGHOME` and `PACKAGE_TARBALL` inherited through `$GITHUB_ENV`), (14) cleanup step `if: always()` (remove passphrase file and GNUPGHOME).
  - `src/release.mjs` (protected mutations, §9 boundaries 4-6, env-driven, all inputs wired from workflow context, none guessed at runtime: `VERSION` from `needs.detect.outputs.version`, `TAG_EXISTS` from the `tag-probe` step output (used as-is; no pre-mutation re-probe, §9 boundary 4), `GITHUB_SHA`, `GITHUB_REPOSITORY`, `GNUPGHOME` and `PACKAGE_TARBALL` inherited through `$GITHUB_ENV`, `NPM_RELEASE_FLOW_GPG_FINGERPRINT` from the repository variable, `NPM_RELEASE_FLOW_APP_TOKEN` from the App-token step output (only when `tag-exists=false`), `GH_TOKEN` from `github.token`): boundary 4 tag push (create-then-verify-then-push with the App token: `git tag -a -s`, full verify of the annotated tag, App-authenticated push via git config extraheader, `ls-remote` equality; tag present -> fetch + verify-only, private material never loaded; divergent -> hard fail), GitHub API signature-verification poll (`gh api .../git/tags/<object>`, polled, `.verification.verified == true`), boundary 5 publish (`npm view` verify-or-idempotent: present -> identity/integrity verify, absent -> refuse if a newer stable version exists on the registry, else `npm publish <verified tarball> --ignore-scripts --access public --provenance`, wait for packument visibility, then the same identity/integrity verify: name, version, repository matching source, `dist.integrity` equal to the packed integrity, `gitHead` checked only when present), boundary 6 GitHub Release (release notes from the changelog section; `gh release view` present -> `edit` (title + notes, idempotent), absent -> `create --verify-tag`).

No new dependencies (zero runtime deps, §3; dev deps stay at typescript + @types/node).

Out of scope: repo settings (initial-setup T5), secret/variable values, first publish, making the repo public, consumer migrations, and any product changes outside `bin/`, `src/`, `.github/workflows/release.yml`, and tests.

## Approach

- One binary, three subcommands, shared core: the CLI and the workflow job scripts are the same kit code (the package is both artifacts' logic, §3); commands and job scripts import the same `src/lib` modules, so local behavior and job behavior cannot diverge. Job scripts are thin env-driven entry points (`GITHUB_OUTPUT`/`GITHUB_ENV` writers); all validation and mutation logic lives in shared, unit-testable modules.
- Dry-run is the default everywhere mutation exists (§8); `--execute` is the only mutation switch. `check` is non-mutating by nature and accepts `--execute` as a no-op for surface uniformity.
- Exit codes 0/1/2 are the programmatic contract (§8): 0 success, 1 error (with the error-content contract), 2 only for genuinely already-done no-ops (open release PR, version already prepared); partial-conflict and manual-action states exit 1. Failures never leave silent half-state: partial failure exits non-zero and its final output states what was created and what remains manual.
- Recoverability is verify-or-idempotent everywhere (observe before mutating; a present mutation is verified, an absent one is performed once, §9): `prepare` refuses per boundary 1/2 state, `tag` verifies an existing tag, the release job verifies present mutations (tag/publish/release) and performs absent ones.
- The workflow owns the trust-boundary plumbing (permissions, step ordering, secret scoping, GPG key material, App token, artifact handoff, toolchain pin); the kit scripts own the logic. Secrets are step-scoped (§6); the release-job order is exactly: consumer checkout at the triggering SHA and guarded kit checkout, toolchain setup + exact-version assertion, tag probe, revalidation #1 and artifact validation, GPG configuration (public or private key per tag-exists), revalidation #2 immediately before tag creation, App-token creation, release mutation, then unconditional cleanup.
- The verify job runs consumer-controlled code (`npm ci`, `npm run release:verify`) and the protected job runs only kit code from the pinned `.npm-release-flow` checkout, executing no repository-owned code and installing no dependency tree (§5, T1); the artifact handoff is the immutable sha256 + pack.json contract (T2).
- The tag probe (job start, after approval) and revalidation #2 (immediately before tag creation) close the TOCTOU window; the probe result is handed to `release.mjs` as `TAG_EXISTS` (no pre-mutation tag re-probe); the tag push itself is the final tag check (a divergent remote tag rejects the push, an identical tag is an idempotent no-op) per §9 boundary 4.
- The skew marker (§10) is a machine-readable line in the release PR body (`Kit: @vipentti/npm-release-flow@<version>`); detect reads it via the merged PR (number resolved from the merge commit message) and fails hard on mismatch, unreadable marker, or unparseable merge message. The lookup runs only on the valid-release branch after classification; ordinary pushes return `is-release=false` and exit 0 without any PR API access. Assumption: GitHub merge commits ("Merge pull request #N from ..."), which is the planlet flow's existing shape; squash-rebase consumers surface as a detect hard fail, documented, not silently degraded (§9 fail-closed rule).
- The local `tag` command is the concept doc's manual recovery mechanism, not the primary release mechanism (PR merge -> protected job -> tag + publish); it resolves the release-merge commit on `origin/main` deterministically (exactly one matching release merge on first-parent history, revalidated by the §9 classification on that commit) before any tag creation, and authenticates its push with the App token exactly like the protected job (T11 holds on both paths), sourcing `NPM_RELEASE_FLOW_APP_ID` from the repository variable and `NPM_RELEASE_FLOW_APP_PRIVATE_KEY` from the local environment, and refuses when either is missing.

## Acceptance Criteria

- `npm-release-flow` with no subcommand, an unknown subcommand, or an unknown flag prints usage to stderr and exits 1; every error message states what was checked, what state was found, and the correction action; no-op/already-done cases exit 2.
- `prepare` dry-run (default) prints every would-mutation, changes nothing, exits 0. `prepare --execute --version X.Y.Z` cuts the changelog, bumps the three version fields, creates the signed commit `release: X.Y.Z` (refuses unsigned), verifies its own commit (message, one parent, signature, changed-file set exactly CHANGELOG.md/package.json/package-lock.json), pushes `release/vX.Y.Z`, verifies the remote ref equals the pushed SHA, creates the PR whose body carries the kit-version skew marker, and returns to `main`. Rerun refuses with distinct messages: already-done states (open release PR, version already prepared) exit 2; partial-conflict and manual-action states (conflicting local/remote branch, closed-unmerged PR) exit 1; partial failure reports what was created and what remains manual.
- `tag` dry-run prints the plan; `tag --execute --version X.Y.Z` creates the annotated signed tag `vX.Y.Z` (subject `Release vX.Y.Z`) on the release-merge commit at `origin/main` (resolved deterministically: exactly one matching release merge on first-parent history, §9-classified as a valid release for the requested version; wrong target refused), fully verifies it (target, subject, exactly one `VALIDSIG` with the configured fingerprint), pushes authenticated with the App token (refuses when `NPM_RELEASE_FLOW_APP_ID`/`NPM_RELEASE_FLOW_APP_PRIVATE_KEY` are unavailable or the token cannot be minted), and verifies the remote object; refuses unsigned or lightweight tags; remote valid tag -> fetch + full verify, exit 0; remote divergent tag -> exit 1; remote absent with a valid local tag -> dry-run reports the push, `--execute` pushes that existing tag with the App token and verifies the remote object; remote absent with no local tag -> create, verify, push, verify.
- `check` exits 0 only when every prerequisite passes (including required-reviewer protection on the `release` Environment and App-tag path readiness), else exits 1 listing every problem; it never mutates anything.
- `detect` maps every §9 enumeration row to its verdict (ordinary push exit 0 `is-release=false` with no PR or skew-marker lookup; valid release exit 0 `is-release=true`+version; each ambiguous row hard fail exit 1), writes the declared outputs, and hard-fails on unparseable merge message, skew-marker mismatch, or unreadable marker, all only on the valid-release branch; missing §4 mandatory consumer prerequisites fail detect before any verdict.
- `verify` runs on the consumer's `engines.node` (Node 22 fallback when absent, §7), runs `npm ci` + `npm run release:verify`, revalidates the §4 mandatory checks (detect enforces them), enforces the pack contract, runs the smoke test, fails closed on T9 skew, and outputs `package-sha256` matching the uploaded tarball.
- The release job body matches §5/§6/§7/§9/§10 step ordering: consumer checkout at the triggering SHA precedes tag probing and revalidation; the pinned toolchain is asserted by exact Node and npm versions; revalidation runs twice (before secrets load and immediately before tag creation); every secret is asserted non-empty in step-scoped checks after non-secret validation, private material never loaded on verify-only reruns; artifact revalidated byte-for-byte; GPG homes fresh and cleanup unconditional; App token is the tag-push identity; all new actions pinned to exact commit SHAs; boundaries 4-6 are verify-or-idempotent with the exact proof conditions of §9.
- actionlint (pinned v1.7.12, existing CI acquisition) is clean on both workflow files; `npm run typecheck` passes; `npm pack --dry-run` lists the new `src` files and the workflow; `planlet validate cli-implementation` passes.

## Risks and Considerations

- Local `tag` needs App credential material: `NPM_RELEASE_FLOW_APP_PRIVATE_KEY` must be present in the operator's environment (secrets are never API-readable) and `NPM_RELEASE_FLOW_APP_ID` must be declared as a repository variable with the App installed on the consumer repository (`contents: write`); `tag` refuses without them. The App-token push satisfies the `refs/tags/v*` creation ruleset, whose only bypass actor is the release App; T11 (App-only tag identity) holds on both the workflow and the local recovery path.
- Skew-marker read depends on GitHub merge-commit messages and a read-only `gh api` call in the unprivileged detect job; both are documented assumptions (§9, §10). A consumer using squash merges fails detect (hard fail), which is the documented fail-closed behavior, not a silent skip.
- The verify job's T9 skew check reads the consumer's installed kit version from `node_modules`; a consumer without the devDependency installed fails there, which is correct (pins must agree, T9).
- `npm publish --provenance` requires the consumer's Trusted Publisher to match the *caller's* workflow filename (§5); the kit cannot enforce that filename, and RELEASE.md already documents it.
- The release job runs kit code from the pinned checkout with no provenance check (§3, documented design decision: checking GitHub against GitHub buys nothing).
